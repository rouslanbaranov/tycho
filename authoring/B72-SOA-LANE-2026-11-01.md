## Candidate evaluation

- OASIS, "Reference Model for Service Oriented Architecture 1.0" (selected;
  existing source src.soa-model). States the ownership-domain definition, the
  description content a consumer needs, the function/policy/information-exchange
  items and the two-party contract definition. Primary evidence for the
  invariant. Technology-neutral: it does not prescribe an interface language, a
  registry protocol, a bus topology or a service size.
- Fowler and Lewis, "Microservices" (selected; existing source src.microservices
  and record read.microservices-article.2026-10-21). States cohesive service
  boundaries and contract-evolution mechanisms, consumer-driven contracts that
  evolve independently, and the ESB facility list. Supporting evidence for the
  invariant and failure/recovery; it criticises ESB complexity but does not
  state a bottleneck, a sizing rule or a failover procedure.
- Microsoft, "Service-Oriented Architectural Style" in Chapter 3 of the
  Application Architecture Guide, 2nd Edition (selected; new unit). States
  independent versioning, shared contracts and schemas, interface compatibility
  and policy-based compatibility. Supporting evidence for the invariant's
  version and contract-boundary claims.
- Microsoft, ".NET Microservices Architecture: Service-oriented architecture"
  (selected; new unit). States that large central brokers, central
  orchestrators and the ESB are typical SOA features and, in most cases,
  anti-patterns in the microservice community. Primary evidence for the
  failure/recovery premise; it does not state a bottleneck measurement, a
  failover procedure or a recovery-time bound.
- Microsoft, "Understanding Service-Oriented Architecture" (considered, not
  bound). Its "formal contract between endpoints places obligations on provider
  and consumer" row is relevant, but the article is CBDI-authored and hosted on
  Microsoft Learn, and the selected Microsoft guide already supplies the
  contract and versioning claims. Adding it would duplicate the unit without a
  distinct claim.
- Azure Cloud Design Patterns (considered, not bound). No SOA contract or
  central-broker failure unit.
- Vendor SOA/ESB tutorials and third-party summaries (considered, not bound).
  They restate the same claims and would add unverified material.
