### Failure and recovery

- Q1, R1, "Solution": "Each geode is behind a global load balancer, and uses a
  geo-replicated read-write service like Azure Cosmos DB to host the data
  plane, ensuring cross-geode data consistency."
- Q2, R1, "Solution": "Geodes aren't the same as clusters because they share a
  replication backplane, so the platform takes care of quorum issues."
- Q3, R2, "Geographic traffic-routing method": "Since a region can be mapped
  only to one endpoint, Traffic Manager returns a response whether the endpoint
  is healthy or not."
- Q4, R2, "Weighted traffic-routing method": "Clients and the recursive DNS
  servers that clients use to resolve DNS names cache DNS responses."
- Q5, R3, "Endpoint failover and recovery": "Clients continue to use the
  endpoint until the DNS cache expires."
- Q6, R3, "Endpoint failover and recovery": "Because Traffic Manager works at
  the DNS level, it cannot influence existing connections to any endpoint."
- Q7, R3, "Traffic-routing methods": "One exception to normal traffic-routing
  behavior occurs when all eligible endpoints have a degraded status. Traffic
  Manager makes a "best effort" attempt and responds as if all the Degraded
  status endpoints actually are in an online state."
- Q8, R3, "How endpoint monitoring works": "Traffic Manager considers an
  endpoint healthy if the probing agent receives a 200-OK response, or any of
  the responses configured in the Expected status code ranges."
- Q9, R3, "How endpoint monitoring works": "For HTTP or HTTPS monitoring
  protocol, a common practice on the endpoint side is to implement a custom
  page within your application - for example, /health.aspx. Use this path to
  perform application-specific checks, such as checking performance counters
  or verifying database availability."
- Q10, R3, "Endpoint failover and recovery": "Traffic manager deploys multiple
  probes from multiple locations for each endpoint." and "Traffic manager
  aggregates the average health of the probes rather than rely on a singular
  probe instance."
- Q11, R4, "Is Traffic Manager resilient to Azure region failures?": "By
  design, Traffic Manager components are resilient to a complete failure of any
  Azure region."
- Q12, R4, "How does the choice of resource group location affect Traffic
  Manager?": "Traffic Manager is a single, global service. It isn't regional."
- Q13, R4, "What is DNS TTL and how does it impact my users?": "a higher TTL
  also means that your data doesn't reflect the latest health information that
  Traffic Manager has obtained through its probing agents."
- Q14, R4, "How can I resolve a 500 (Internal Server Error) problem when using
  Traffic Manager?": "When a service endpoint is unresponsive, clients and
  applications that are using that endpoint don't reset until the DNS cache is
  refreshed."
- Q15, R5, "Data replication and latency": "Active-active patterns with
  bidirectional writes require conflict resolution strategies at the
  application or database layer. The network provides connectivity, but
  applications must handle write conflicts."
- Q16, R5, "Data replication and latency": "Cross-region replication introduces
  network latency that affects application design."
- Q17, R5, "Data replication and latency": "Choose synchronous replication only
  for region pairs with low latency (< 10 ms). Use asynchronous replication for
  distant pairs to avoid application performance degradation."
- Q18, R6, "Recommendations": "Replication to the secondary region is
  asynchronous, so include possible replication lag and storage-account
  failover in your recovery design."
- Q19, R6, "Cross-region replication": "These options replicate data
  asynchronously, so the RPO varies. Monitor Last Sync Time to understand
  current replication lag."

### Alternative

- Q20, R5, "Active-active": "Both regions serve traffic simultaneously. A
  global load balancer, such as Traffic Manager or Front Door, distributes
  requests across regions based on proximity, performance, or weight."
- Q21, R5, "Active-active": "Your application can handle requests in any region
  without region-specific state dependencies."
- Q22, R5, "Active-active": "You need the lowest possible RTO (failover is
  immediate because the healthy region already serves traffic)."
- Q23, R5, "Active-passive": "One region (primary) handles all traffic. The
  secondary region stays ready but doesn't serve user requests until a failover
  event."
- Q24, R5, "Active-passive": "Your application has strict write-region
  requirements or can't easily replicate state."
- Q25, R5, "Active-passive": "Cost constraints prevent running full capacity in
  two regions simultaneously."
- Q26, R5, "Active-passive": "Your RTO tolerance allows for the time needed to
  activate the secondary region."
- Q27, R5, "Active-passive": "Test failover regularly. Network configurations
  in the passive region can drift if not validated."
- Q28, R5, "Choosing between active-active and active-passive networking":
  "Continuous, bidirectional replication traffic" and "One-directional async
  replication to standby".
- Q29, R6, "Active-active architecture": "Active-active architectures spread
  incoming traffic across identical web apps in multiple separate regions."
- Q30, R6, "Active-passive architecture": "Active-passive architectures use
  identical web apps in multiple separate regions, but Azure Front Door routes
  traffic to only one active region at a time."
- Q31, R5, "Security considerations": "Traffic Manager failover depends on DNS
  TTL. Shorter TTLs enable faster failover but increase DNS query volume. Front
  Door provides connection-level failover that doesn't depend on client DNS
  cache expiration."
- Q32, R5, "Active-active": "DNS TTL and health probe intervals determine how
  quickly Traffic Manager shifts traffic."
- Q33, R5, "Active-passive": "Automated failover requires health probes with
  appropriate thresholds (avoid flapping)."

The eight quoted fragments in the book are: "distributes request processing
around the globe to improve latency and increase availability" (R1),
"never exist in isolation" (R1), "until the DNS cache expires" (R3),
"returns a response whether the endpoint is healthy or not" (R2),
"best effort" (R3), "strict write-region requirements or can't easily
