# Command Query Responsibility Segregation (CQRS)

**Identity.** CQRS; family Data consistency, transactions and event sourcing; kind
architecture-pattern; priority core.

**Decision question.** Should command and query models be separated so reads and writes
can evolve independently?

**Good-fit conditions.** Read and write workloads differ; projections can be asynchronous;
stale reads are acceptable; duplicate/order handling is owned; Tycho guidance: the write
model remains the only authority for command-owned state.

**Hard contraindications.** Reject when one model meets both needs, when every read requires
immediate consistency with no version-wait or authority-read path, or when projection
maintenance has no owner.

**Competing alternative.** Single model with indexes/views. Revisit the separation when
command contention, projection lag or rebuild duration outweighs the read benefit, and prefer
one model when that case cannot be made.

**Failure and recovery.** Microsoft documents eventual consistency, recommends making the
read-model consumer idempotent to tolerate duplicate delivery, and requires an outbox to
persist the state change and event atomically; Microsoft documents that read data can lag,
and says views can be regenerated by replay. Tycho guidance, not a source claim: commit the
derived row and its cursor atomically, disable outbound side effects during rebuild, and
treat cursor gaps and schema drift as explicit failure states.
